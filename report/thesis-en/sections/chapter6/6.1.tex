\section{Evaluation and Choice of Technologies and Models}
\label{sec:6.1}

The options were judged on four criteria: the requirements of Chapter~\ref{chapter:phantich}; running on a CPU-only machine with 16~GB of memory; an open-source licence suited to a non-commercial project; and the developer's familiarity, to limit risk. \subsection{Front-End Technologies}
\label{sec:6.1.1}

The interface has many interactions on one screen, such as dragging a query image, re-sorting results or opening dialogs over the list, which suits a \emph{single-page application} that loads once and then only exchanges data through the API. React was chosen for its ecosystem of routing, API and styling libraries, with Vite for bundling and Tailwind CSS for a consistent layout that adapts to phones.

\subsection{Server-Side Technologies}
\label{sec:6.1.2}

The server and the worker are written in Python, the language of all the project's models, so the server can load the query encoder directly and share data access code with the worker. Django is heavier than an API-only server needs, and FastAPI's asynchronous advantage matters little once video analysis has left the server (Section~\ref{sec:5.1.3}); Flask is small, explicit and familiar to the developer. With a single sequential worker, a PostgreSQL table replaces Celery with Redis or RabbitMQ, saving memory on the target machine.

\subsection{Database and Storage}
\label{sec:6.1.3}

PostgreSQL provides what the design relies on: complex CHECK constraints, partial indexes, JSONB for logs and metrics, and \texttt{SKIP LOCKED} for safe job claiming. For vectors, pgvector~\cite{pgvector2026} would need only one database, but with an approximate index it filters \emph{after} the scan and may return too few results (Section~\ref{sec:3.6.3}); FAISS is an in-memory library that leaves storage, filtering and concurrency to the application. Milvus~\cite{wang2021milvus} filters before searching~\cite{milvus2026filtered}, which directly serves area-based access control; it needs etcd and an object store, but all services in Docker use only under 0.4~GiB of memory (Section~\ref{sec:8.7}). Frames go to MinIO rather than plain files for per-bucket access control and per-object hashes, sharing the MinIO server Milvus already needs, in a separate bucket.

\subsection{AI Models}
\label{sec:6.1.4}

\paragraph{Person detection.} Two-stage detectors such as Faster R-CNN are too slow on a CPU, so the YOLO family was chosen. Within YOLO11, size sets the CPU speed (Table~\ref{tab:yolo11-sizes}), and even YOLO11n leaves the pipeline about seven times slower than real time (Section~\ref{sec:7.2}), so the smallest size was chosen, with a low confidence threshold and tracking compensating for accuracy. YOLO11's AGPL-3.0 licence suits a non-commercial project but not a product, so YOLOX~\cite{ge2021yolox} (Apache-2.0) is registered as a fallback.

\paragraph{Tracking.} Algorithms that add appearance features, such as DeepSORT~\cite{wojke2017deepsort} and StrongSORT~\cite{du2023strongsort}, hold tracks better through long occlusions but run an extra model for every person in every frame, too heavy for a CPU in crowded scenes. With static cameras, ByteTrack~\cite{zhang2022bytetrack} is the default, and BoT-SORT~\cite{aharon2022botsort} an alternative with ReID and camera motion compensation disabled.

\paragraph{Encoder.} Separate image and text models would mean two vectors per appearance and two models during indexing, and general models such as CLIP~\cite{radford2021clip}, including multilingual variants for Vietnamese, were expected to separate small clothing differences less well. RaSa~\cite{bai2023rasa}, recommended by the supervisor, serves all three forms of query with one vector per appearance (Section~\ref{sec:3.5.4}), at the cost of English-only queries. Section~\ref{sec:8.4} evaluates it on the project's data and, after the fact, against CLIP on the same data: RaSa is far better for image queries and CLIP far better for text queries, so the expectation held for one form and not the other. Part~II of this report studies a different choice for text queries, CLIP ViT-H/14 followed by a reasoning layer, outside the application (Chapter~\ref{chapter:r-overview}).
