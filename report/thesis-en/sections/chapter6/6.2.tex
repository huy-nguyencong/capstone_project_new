\section{Background AI Worker Implementation}
\label{sec:6.2}

Building on the job flow of Section~\ref{sec:5.2.1}, this section covers how the worker runs reliably on a CPU-only machine.

\subsection{Model Management and Packaging}
\label{sec:6.2.1}

Only models declared in a \emph{model registry} are loaded; each entry records an identifier, version, weight file with its SHA-256 hash, preprocessing version and provenance with the licence, and Trackers list their compatible Detectors. A model is usable only if its weight file exists, the hash matches, the licence is approved and a trial load succeeds; others are shown as \emph{Unavailable}. YOLO11n, ByteTrack, BoT-SORT and RaSa are usable, while the larger YOLO sizes and YOLOX have no weight files yet. The hash is rechecked whenever a pair is selected, so a replaced weight file cannot be used silently; a new configuration is trial-loaded before saving, and each job keeps the configuration version current at its creation.

The RaSa checkpoint is loaded selectively. Its state is read from the file through a memory map, only the entries of the image encoder, the text layers of the text encoder and the two projections are kept, and they are assigned to a module created without initial weights, so no random weights are allocated and then overwritten. A check against the original loading code on 50 person crops and 10 sentences gives identical vectors, so the vector space and the encoder version are unchanged. The steady memory of one loaded encoder falls from about 2.2~GiB to about 0.9~GiB, and the peak while loading from about 3.9~GiB to about 0.9~GiB (Section~\ref{sec:8.7}).

Each kind of model sits behind an \emph{adapter} with a common interface (open, process one input, close) that also checks the output: the Detector keeps only valid person boxes, and RaSa vectors must have 256 normalised, valid dimensions. Adding a model such as YOLOX thus needs only its weight file and a registry entry, plus an adapter for a new kind of model.

\subsection{Resource Limits and Error Handling}
\label{sec:6.2.2}

The worker is bounded at several levels. Numerical libraries use 2 threads, leaving CPU cores for the server and the data stores. The Detector and image encoder run in a child process that is killed if an inference exceeds 120 seconds, since a call hung in a native library cannot be interrupted from inside. Each job runs in its own process with a 3,600-second deadline, and the operating system reclaims all its memory when it ends. Frames are released as soon as they are processed, except the bounded representative frame candidates.

Each error carries its step and an error code, stored with the job for the administration screens, and is classified in advance as \emph{transient} or \emph{unrecoverable}. Transient errors of video jobs are retried from 5 seconds doubling up to 300 seconds, at most three times; RTSP sessions are not retried, since that video has passed (Section~\ref{sec:5.2.1}). On a stop signal, the running job stays \emph{Running} so it can be reclaimed after its lease expires, and a global PostgreSQL lock ensures a single executing process even if the worker is started twice.

\paragraph{AI check.}\label{sec:6.2.5} The \emph{AI check} screen trial-runs the models on real data without creating a job: for a camera, it reads up to 90 RTSP frames and runs the Detector, Tracker and image encoder on 6 of them; for search, it encodes a sample image and description. A check takes at most 180 seconds, one at a time.
