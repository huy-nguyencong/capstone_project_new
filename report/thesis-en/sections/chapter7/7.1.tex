\section{Environment and Deployment Procedure}
\label{sec:7.1}
\label{sec:7.3}

\paragraph{Environment.} The whole system is deployed on a laptop with an Intel Core i5-11300H processor (4 cores, 8 threads, 3.1~GHz), 16~GB of memory and no discrete graphics card, running Windows 11. The infrastructure services run in Docker Compose: PostgreSQL 17, Milvus 2.6 in Standalone mode with etcd, MinIO shared by Milvus and by the application's frames, and MediaMTX to stream the simulated cameras. The Flask application server and the background worker run directly on the machine; the React web application is built once and its static files are served by the application server on the same origin, so no development server, proxy or cross-origin configuration is needed during the demonstration. The WSL~2 virtual machine behind Docker Desktop is capped at 3~GB of memory, since by default it may claim up to half of the machine's memory while the containers need about 0.5~GiB (Section~\ref{sec:8.7}). The AI configuration is YOLO11n with a confidence threshold of 0.1, ByteTrack, the RaSa encoder and a sampling interval of $N = 20$, all running on the CPU.

\paragraph{Start-up procedure.} Components start in order: infrastructure, camera streams, application server (which also serves the web application), background worker. A warm-up search loads the query encoder before use (Section~\ref{sec:8.7}).

\paragraph{Backup and restore.} The backup of the demonstration data of the three stores is about 510~MB in 1,525 files. The restore procedure was rehearsed with 1,555 tracks, 10 of whose frames had been deleted on purpose: the restore finished in 28.8 seconds (PostgreSQL 1.8 seconds; frames 6.2 seconds, with all 10 of 10 files re-uploaded; rebuilding the Milvus vectors 8.8 seconds; reconciling the three stores 12 seconds). The first rehearsal, writing vectors one by one, took 1,485 seconds with one vector timing out, which led to batch writes. After each demonstration rehearsal, the data is reset in about 70 seconds.
