\section{Application Programming Interface Design}
\label{sec:5.4}

The web application uses a REST-style API under \path{/api/v1}, with plural resource names such as \path{/cases} and Administrator APIs under \path{/admin}. Data is JSON, except images and videos sent as \texttt{multipart/form-data}. Business state changes such as retiring a camera are explicit actions, for example \texttt{POST} \path{/admin/cameras/{id}/retire}, each checked and logged on its own.

Errors share one format: a stable \emph{error code}, a Vietnamese \emph{message}, \emph{details} such as per-field errors, and a \emph{request identifier} matching the server log. Status codes keep their standard meaning: 401 without a valid session, 403 for a disallowed role, 404 for a missing or out-of-scope resource, 409 for a state conflict, 422 for invalid data and 429 over the call limit.

Updates to accounts, cameras and cases carry the version number held by the interface and get 409 if the data changed elsewhere. A video upload may carry an idempotency key, so a resend creates no second job, and is asynchronous: the server returns 202 with the job, whose progress the interface then follows.

A search response states whether the re-ranking stage of Section~\ref{sec:5.2.3} was applied, since it changes what the relevance score means. No API takes the Operator's area or the case owner as a parameter (Section~\ref{sec:5.5.3}). Images of search results and of saved results have separate paths, matching the two grounds of Section~\ref{sec:4.6}.

Three health-check paths (\path{/health/live}, \path{/health/ready}, \path{/health/storage}) serve deployment and monitoring.
