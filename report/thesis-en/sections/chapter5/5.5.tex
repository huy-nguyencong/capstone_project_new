\section{Security and Access Control Design}
\label{sec:5.5}

The security requirements of Section~\ref{sec:4.3.1} and the permission matrix of Section~\ref{sec:4.6} are implemented in \emph{defence in depth}: each request is checked for its session, role and data scope, and database constraints are the last layer.

\subsection{Authentication and Sessions}
\label{sec:5.5.1}

Passwords have at least 8 characters and are hashed with Argon2. An unknown username is still verified against a dummy hash and gets the same error as a wrong password, so neither timing nor message reveals which usernames exist.

A successful login yields a random 32-byte token in a cookie that is \texttt{HttpOnly} (unreadable by page scripts), \texttt{SameSite=Lax} (not sent with data-changing requests from other sites) and \texttt{Secure} over HTTPS. The database stores only its SHA-256 hash, so a leaked session table holds no valid token. A request gets 401 if its session is revoked, older than 12 hours or idle for 30 minutes, and the session is revoked at once if the account is locked, deactivated or an Operator without an area. While the user is active, the interface refreshes the session; each refresh issues a new token with its own 12-hour limit and revokes the old one, so a leaked token is short-lived.

\subsection{Cross-Site Request Forgery Protection}
\label{sec:5.5.2}

Because the browser sends the cookie automatically, another website could make it send requests to the system (CSRF). Besides \texttt{SameSite}, every data-changing request must carry an \texttt{X-CSRF-Token} header, an HMAC-SHA256 of the session token given to the interface at login, which other sites cannot read. Only the configured origins may call the API with cookies (CORS), and responses carry security headers that disable content-type sniffing, framing by other sites and caching.

\subsection{Access Control}
\label{sec:5.5.3}

Access control has three server-side layers. Each API declares its allowed roles and rejects others with 403 before any processing. The business layer then checks each object: cameras and appearances in the Operator's current area and operational, cases owned by the Operator, and images on one of the two grounds of Section~\ref{sec:4.6}; the area and owner always come from the session, never from the request, so editing a request cannot widen the rights. Finally, database constraints stop invalid data even if the business layer has a bug.

Objects outside the scope get 404 rather than 403, so trying identifiers reveals nothing about which objects exist.

\subsection{Data Protection and Abuse Limitation}
\label{sec:5.5.4}

RTSP credentials are separated from the address, encrypted with Fernet under a key from an environment variable and decrypted only to connect; they are never returned or logged. Since the connection check makes the server connect to a user-given address, only IP addresses in the declared camera ranges are accepted, and loopback, link-local and multicast addresses are always refused, so the check cannot probe the internal network (SSRF).

Costly or probe-prone functions are limited per minute: login 10 times per IP-username pair, and per account search 30, video upload 10, connection check 10 and AI check 6 times; beyond that the server returns 429 with the waiting time. The counters live in process memory, which suits the single-process deployment. Query images must be JPEG or PNG within 10~MB and 24 megapixels, videos within 500~MB with a valid signature, and user file names are never used as storage paths.
