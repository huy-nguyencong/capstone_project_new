\paragraph{Relationships.} Most foreign keys are mandatory: a camera has one area, a case one owner, and an appearance one camera, one job and one AI configuration version. Three may be null: only Operators have an area, only upload jobs have a requester, and a log entry such as a technical error may have no user. \texttt{cases} and \path{person_tracks} have a many-to-many relationship through \path{case_results}. Each row of this table has its own primary key, stores a snapshot of the information at the time of saving, and has \emph{no} uniqueness constraint on the case-appearance pair, since each save creates a new entry.

\paragraph{Integrity constraints.} Many business rules are enforced by the database itself, so a bug in the application cannot write invalid data:
\begin{itemize}
    \item An Operator account always has an area and the other two roles never do; a case has a closing time if and only if it is \texttt{CLOSED}; only one AI configuration version is \texttt{ACTIVE}; the area code and the area of a camera do not change after creation.
    \item Most foreign keys use the RESTRICT rule, so data that is still referenced cannot be deleted; accounts and cameras are not deleted but change status (\texttt{INACTIVE}, \texttt{RETIRED}). Only login sessions and result entries are deleted with their parent.
    \item An appearance can only be \texttt{READY} when it has the object key, hash and size of its frame and the time its vector was written. No table stores a relevance score.
    \item The \texttt{users}, \texttt{cameras} and \texttt{cases} tables have a version column to prevent overwriting on concurrent updates (Section~\ref{sec:5.2.4}); the requester-idempotency key pair of \path{processing_jobs} is unique, so a repeated upload request creates no additional job.
\end{itemize}
Indexes serve the frequent queries, such as appearances by camera and time, cases by owner and log entries by actor.

\subsection{Feature Vector Storage}
\label{sec:5.3.2}

Milvus only finds the vectors closest to a query within a filtered scope; everything else, permissions included, lives in PostgreSQL.

\paragraph{One collection per encoder version.} Each encoder version has its own Milvus \emph{collection}, such as \path{person_track_embeddings_rasa_cuhk_pedes_v1}, because vectors of two versions cannot be compared. A fixed alias points to the collection in use, and its dimension is checked when the worker starts. Each appearance corresponds to one record with the fields of Table~\ref{tab:milvus-schema}.

The area, camera and time are copied from PostgreSQL for pre-filtering (Section~\ref{sec:3.6.3}); a camera's area never changes, so the copy cannot diverge. The operational status does change and is not copied: each search puts the current list of operational cameras into the filter, so a retired camera is hidden at once without touching Milvus.

\paragraph{Index and operations.} The vector field has an HNSW index with the inner-product metric, $M = 16$, \textit{ef\-Con\-struc\-tion}~$= 128$, and $\mathit{ef} = 64$ at search time (Section~\ref{sec:3.6.4}). Vectors are written by \emph{upsert} on the appearance identifier, so retries create no duplicates, after checking their dimension, values and unit length; strong consistency makes a new vector visible to the next search.

\subsection{Frame Storage}
\label{sec:5.3.3}

Each appearance has one file in MinIO, its representative full frame as JPEG at quality 90; PostgreSQL keeps the object key, hash and size. Person images are not stored but rendered from the frame and box on request (Section~\ref{sec:6.3.3}), so one file serves both views, cropping can change without new data, and no loose person images exist. The original video is not stored.

The key of each file is derived deterministically from the appearance, following the pattern
\begin{center}
\texttt{tracks/v1/}\allowbreak \textit{camera code}\texttt{/}\allowbreak \textit{year}\texttt{/}\allowbreak \textit{month}\texttt{/}\allowbreak \textit{day}\texttt{/}\allowbreak \textit{appearance id}\texttt{/}\allowbreak \texttt{representative.jpg}
\end{center}
so a retry rewrites the same file; the versioned prefix allows a later change of layout, and grouping by camera and day eases clean-up.

Each file is checked for format, size (at most 20~MB) and dimensions, and its SHA-256 hash is kept in both stores: an existing key with the same hash is reused, a different hash is a conflict, and reads recompute the hash to detect corruption. The bucket is private, accessed by an account limited to it, and never exposed to the browser.

\subsection{Consistency Across the Stores}
\label{sec:5.3.4}

An appearance is stored in three parts across three stores that share no transaction, so writing may stop midway or a store may be unreachable. The system guarantees that incomplete data never appears in results and can later be completed or detected.

\paragraph{Appearance states.} Each appearance has a synchronisation state with the transitions of Figure~\ref{fig:track-state}; only \emph{Ready} appearances are searched, and other transitions are rejected.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth]{H6-trang-thai-lan-xuat-hien.png}
\caption{State diagram of an appearance}
\label{fig:track-state}
\end{figure}

\paragraph{Write order.} An appearance is written in a fixed order:
\begin{enumerate}
    \item In \emph{one} PostgreSQL transaction, create the record in the \emph{Pending} state and an event in \path{storage_outbox_events} holding everything that must be written to the other two stores, the vector included. This is the \emph{transactional outbox} pattern: the intent to write to another system is stored in the same transaction as the main data.
    \item Write the frame to MinIO under its deterministic key.
    \item Write the vector to Milvus, then read it back to confirm the record exists with the right area and camera.
    \item In a new transaction, move the record to \emph{Ready}, store the hash and size of the frame and the time the vector was written, and mark the outbox event as done.
\end{enumerate}
Writing PostgreSQL \emph{first} means every frame and vector matches a known record, so anything else is orphaned; setting \emph{Ready} \emph{last} means an appearance is found only when complete. Steps 2 and 3 can be repeated safely thanks to the deterministic key and the upsert.

\paragraph{Error handling and maintenance tools.} A transient failure in step 2 or 3 leaves the record \emph{Pending} and schedules a retry, from 2 seconds doubling up to 300 seconds. After five attempts, or on an unrecoverable error such as a hash conflict, the record becomes \emph{Failed} and is logged. Since the outbox event holds all the data, retries never rerun the analysis. Operators also have a command-line tool to complete pending appearances; to reconcile the three stores, finding records pending for too long, ready records missing their frame or vector, and orphaned data (by default it only reports; on request it quarantines broken records and deletes orphans); to move a failed appearance back to pending; and to rebuild the Milvus data from the outbox events. These commands are currently run by hand.

\paragraph{Protection at search time.} Even when the stores are out of sync, users see no wrong data: every Milvus result is checked against PostgreSQL, and missing or out-of-scope results are dropped (Section~\ref{sec:3.6.4}).
