With $N = 20$, CPU time drops by about a quarter and the image size by about a third, while the number of short tracks, a sign of broken tracks, hardly changes. Processing time drops only about 9\%, because most of it is spent in the image encoder, about 1.85 seconds per track against 0.16 to 0.23 seconds per sampled frame for the Detector; it therefore depends mainly on the number of people in the video. The benchmark video is more crowded than the demonstration data: 36 tracks in 10 seconds, against 752 tracks in 420 seconds of video from the seven cameras in the 60-120 second segment (Section~\ref{sec:7.2}). The ratio of processing time to video length is therefore higher here than the roughly sevenfold slowdown measured when indexing the demonstration data. Model process memory barely differs, since it mostly holds weights. As a CPU-only machine is already far slower than real time, $N = 20$ stays the default (Section~\ref{sec:3.4}).

\paragraph{RTSP stream handling.} The ingestion of simulated RTSP streams was verified in three situations, with a confidence threshold of 0.25, so the track counts are only indicative: a normal session processed 300 frames, produced 29 tracks and a text search returned 8 results, in 136 seconds; when the streaming source was cut for 5 seconds mid-session, the background worker reconnected once and continued, completing 600 frames with 38 tracks in 140 seconds; when the Administrator disabled AI processing mid-session, the job became \emph{Cancelled} and left no incomplete track. With the current configuration, in the rehearsals, a newly added RTSP camera was \emph{Online} and the background worker created a processing session 13 to 24 seconds after AI processing was enabled.

\paragraph{Timestamps of RTSP frames.} Until 5 October, RTSP frames were timestamped with the time the system received them. Since analysis runs about seven times slower than the stream, two processed frames were then further apart in the stored timeline than in the camera's: on the simulated stream of camera C1, reading 300 frames with an emulated processing time of 100 milliseconds per frame and the sampling interval $N = 20$, consecutive processed frames were a median of 2,456 milliseconds apart by the reception time, above the two-second termination rule for all 14 pairs, but 334 milliseconds apart by the stream's own timestamps, the true spacing of 20 frames at 60 frames per second. The source now uses the stream timestamps (Section~\ref{sec:3.7.4}); with processing as fast as the decoder, both methods agree (409 against 334 milliseconds, the difference being decoding jitter). The track termination rule therefore no longer depends on the processing speed, and the 35 RTSP tracks of the demonstration data, indexed before this change, keep their reception-time timestamps.

Search by image is over ten times slower because the query image goes through RaSa's image encoder on the CPU, while a description only needs the text encoder. With the re-ranking stage of Section~\ref{sec:8.4} enabled, a text or attribute search costs one fusion pass per candidate on top, about 0.15 seconds each with the image tokens of the demonstration data precomputed (about 1.3 seconds per track once, 1.4~GB on disk for 1,523 tracks), hence about 9 and 17 seconds for 64 and 128 candidates; without the cache the first search over a candidate pays its image encoding as well. Through the interface in the rehearsals, the first search after start-up took about 31 seconds, mostly to load the encoder. Later searches took about 8 seconds, as they were measured while the worker ran an RTSP session and include the rendering time. Without warm-up and with a busy worker, the first search took about 97 seconds, which is why the deployment procedure includes a warm-up search (Section~\ref{sec:7.1}).

\paragraph{Storage and memory.} Each track takes about 358~KB on average for its full JPEG frame and 1~KB for its 256-dimensional vector; the relational database is about 24~MB. The application processes fell from about 7.9~GiB to about 4.3~GiB while a job runs, for three reasons. The application server holds 0.6~GB of RaSa weights instead of the 1.9~GB training checkpoint. The image encoder process of the pipeline no longer allocates random weights before copying the checkpoint, so its peak fell from about 3.9~GiB to about 1.0~GiB, next to about 0.4~GiB for the detector process and 0.7~GiB for the main process. And the Vite development server is no longer needed. The Docker virtual machine is listed separately because its figure is mostly the Linux page cache inside the machine and depends on how long it has been running: 0.8~GiB after a long uptime on 29 September, 3.2~GiB right after a restart on 5 October and 1.7~GiB forty minutes later; the 3~GB cap of Section~\ref{sec:7.1} bounds it without shrinking it.

The memory figures come with four conditions. First, to avoid writing into the demonstration data, the processing state was measured with a tool that runs exactly the system's analysis pipeline on a 10-second video in place of the background worker. Second, the pipeline peaks (4,772 and 2,098~MiB) add the peaks of the main process and the model processes, which may not occur at the same time, so they are upper bounds; the 5-second sampler of the whole-stack measurement saw 3,313 and 1,936~MiB. Third, on Windows, the measured memory is the part currently in RAM, which the operating system may trim when RAM runs low. Fourth, other applications were open during both measurements, so the RAM used by the whole machine rose from 13.2~GiB when idle to 15.2~GiB while processing on 29 September, and from 13.7 to 15.1~GiB on 5 October, out of 15.7~GiB. The largest remaining item is the query encoder, which the application server and the worker still load separately, about 1~GiB each with the PyTorch runtime; unneeded applications should still be closed during a demonstration.
