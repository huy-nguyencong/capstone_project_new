Abstract
When a person must be found in the data of a surveillance camera system, operators usually review the video by hand, which takes a long time and easily misses things as the number of cameras and the recording time grow. This project builds a web application that helps search for people in camera data, letting the user describe the person in one of three forms: a reference image, an English description, or a set of predefined appearance attributes. The system only proposes and ranks results the decision whether a result is the person being sought remains with the user.
The application has two flows. The indexing flow runs in a background worker: video from an RTSP stream or an uploaded file is sampled, people are detected with YOLO11n and tracked with ByteTrack to group the frames of one person into an appearance, and the representative frame is encoded into a vector with the RaSa model. The data is written to three stores: PostgreSQL for the business data, Milvus for the vectors and MinIO for the frames. The search flow runs in a Flask application server: the query is encoded into the same vector space and matched only within the cameras the user is allowed to see. A React web application serves three roles, the Administrator, the Operator and the Viewer, with functions for managing cameras and AI models, searching, viewing results in their original frame and saving results into case files.
The application was deployed on a CPU-only laptop and tested with the seven cameras of the WILDTRACK dataset, of which 1,488 tracks from the first 120 seconds of each video were indexed without errors. It passes 740 unit tests together with integration and end-to-end tests, and the demonstration script for all three roles ran automatically twice in a row with 15/15 steps passed. Search by image performs well, while search by text and by attributes by the vectors alone is nearly ineffective, mainly because the model's accuracy lies in its cross-modal re-ranker adding that re-ranker over the first 128 candidates raises Recall@8 of text search from 0 to 0.423 at about 17 seconds per
v

query on the CPU. The analysis is about seven times slower than real time, so the system processes the cameras in turn.
To address the weakness of text search, the second part of the project studies a semantic reasoning layer on top of CLIP retrieval. Each person crop is described offline by a vision-language model (Qwen2.5-VL-3B) into eighteen human-readable attributes with per-region image-quality statistics at query time, CLIP returns a candidate pool and a multi-agent funnel driven by a small language model (Gemini Flash-Lite) re-ranks it from the attribute evidence, over a coarse and a fine round. On 100 identities of a 496-identity subset of Market-1501, the four-stage funnel raises R@10 from 33.0% for CLIP to 56.0%, rescuing 28 of the 67 identities CLIP missed while losing 5 of the 33 it had found. Together, the two parts show that a complete multimodal person search system can be built from existing models on commodity hardware, and that reasoning over readable attribute evidence is a promising way to improve its weakest form of search.

Chapter Summary
The report has a shared introduction, two parts carried out by different members (see the Work Contribution page), and a shared conclusion.
Chapter 1: Introduction Presents the difficulty of finding a person in a large amount of surveillance video by manual review, and sets the objectives of building an application that searches for people by image, description or appearance features, and of studying how to improve search from text descriptions. It also defines the scope and the limitations of the project.
Part I: The Person Search Application
Chapter 2: Related Systems Surveys three commercial systems that search for people in video, BriefCam, Avigilon and Verkada, compares them on criteria relevant to the project, and derives the directions of the system.
Chapter 3: Theoretical Background Presents person search and cross-modal retrieval and the techniques the application uses: person detection, multi-object tracking, frame sampling, joint image-text representation learning with the RaSa model, vector search with the HNSW index, and the RTSP protocol used to simulate cameras.
Chapter 4: System Analysis Defines the three actors, the Administrator, the Operator and the Viewer, lists the functional and non-functional requirements, presents the use case diagram and the specifications of the main use cases, and ends with the permission matrix.
vii

Chapter 5: System Design Presents the architecture that separates the AI processing from the application server, the two main flows of indexing and search, the data design over the PostgreSQL, Milvus and MinIO stores, the application programming interface, the security mechanisms and the user interface design.
Chapter 6: System Implementation Explains the choice of technologies and models, describes the implementation of the background AI worker and the web application, presents the main screens by role, and the operation monitoring tools for the Administrator.
Chapter 7: System Deployment Describes the deployment environment on a CPU-only laptop, the start-up, backup and restore procedures, and the preparation of the demonstration data from the seven cameras of the WILDTRACK dataset.
Chapter 8: Testing and Evaluation Presents the results of testing at five levels, from unit tests to the demonstration script, the evaluation of the three forms of search, and the measurements of the sampling interval, RTSP handling, search latency, storage and memory. It then traces the weakness of text search to its causes with a check of the encoder on its own training data, a diagnosis of the camera crops, the model's re-ranking stage over the vector candidates and a comparison with CLIP on the same data.
Part II: Semantic Reasoning for Text-Based Person Search
Chapter 9: Semantic Reasoning: Motivation and Overview States the problem and the contributions of the research, reads the pipeline as a template of replaceable blocks, argues for improving the search block with a reasoning layer inspired by ZARA, and fills each block with a concrete model.
Chapter 10: Attribute Index and Multi-Agent Reasoning Describes the attribute index built with a vision-language model and the four-stage multi-agent funnel that re-ranks the CLIP candidate pool from that evidence.
viii

Chapter 11: Experiments and Results Presents the experimental setup on Market-1501, the results against the CLIP baseline decomposed into rescued and lost identities, a targeted re-run on a larger model, the ablations of the prompt mechanisms and the evaluation tooling.
Chapter 12: Conclusion and Future Work Presents the timeline of the project with the member responsible for each task, summarises the results of both parts against the objectives, the limitations confirmed by the experiments and the directions for future work, including how the two parts could be brought together.

Chapter 1
Introduction
This chapter presents the context of the project and the reasons for choosing it, the objectives it pursues, its scope and its limitations.
1.1 Motivation
Surveillance cameras are being deployed more and more widely in Vietnam. According to figures from the General Department of Customs cited by the Ministry of Information and Communications, more than 16 million surveillance cameras were imported into Vietnam over the last five years, about 3.2 million a year on average, and the country is estimated to have more than 20 million surveillance cameras in use by 2025 [1]. The large number of cameras and their continuous recording produce a very large volume of video.
The value of a camera system does not lie only in deterrence. A review of forty years of research found that surveillance cameras reduce crime by a modest amount [2], but their more prominent role is to provide evidence for tracing events after they happen. A study of 251,195 incidents recorded by the British Transport Police found that camera footage was useful to the investigation in about 29% of cases, and that when useful footage was available, the share of cases solved rose from about 20% to about 50% [3]. The practical value of camera data therefore depends heavily on whether the right footage can be found.
Many organisations record continuously and need to find when and where a specific person appeared, but reviewing every video by hand is slow and error-prone. When cameras span several areas, searching is usually assigned by area and results are kept in
1

case files for managers, which adds needs for access control and result management. The initial information about the person is also often incomplete and comes in dif-
ferent forms: a reference image, a verbal description, or a few features such as gender, clothing type and colour, or carried items. A useful system should accept all these descriptions in one matching mechanism rather than a single form of query.
These practical needs motivate the project "Developing a Person Search System from Multimodal Descriptions".
1.2 Objectives
The overall objective is an application that helps users search for people in surveillance camera data by describing them in several ways instead of reviewing video by hand. The system proposes and ranks results the decision whether a result is the person sought remains with the user.
The specific objectives are:
1. Turn camera data into searchable data. Automatically analyse the camera images, detect and track people, and store each appearance of a person as a searchable unit.
2. Search for people with multimodal descriptions. Describe the person with a reference image, a sentence or predefined appearance features, all matched against the analysed data and ranked by relevance.
3. Support the assessment and management of search results. Review each result in its original context and save confirmed results into case files for follow-up.
4. Operate safely with many users. Grant permissions by responsibility, limit each person's searches to their assigned area, and provide administration and monitoring functions.
5. Assess the applicability of existing artificial intelligence models. Without training new models, select published models suited to the problem and to commodity hardware, and evaluate their search quality and processing cost in the application.
2

6. Study how to improve search from text descriptions. Separately from the application, the project investigates a reasoning layer that reads human-readable attribute evidence about each candidate and re-ranks the results of text-based search, and measures what it gains and what it costs against a conventional retrieval baseline.
The project is considered to have met its objectives when the application runs the whole workflow, from receiving camera data, searching and assessing results to saving case files, with measurements of search quality and performance presented in Chapter 8, and when the reasoning layer of objective 6 has been evaluated as reported in Chapter 11.
1.3 Scope
The scope of the project is as follows.
Search target. The system only searches for people. Search is based on overall appearance, such as clothing, colours and carried items, not on faces or other biometric features.
Camera data. The system receives camera video over the Real Time Streaming Protocol (RTSP), the common protocol of surveillance cameras. The cameras are simulated by streaming the videos of a public dataset of seven static cameras observing one place each stream acts as one camera assigned to a surveillance area, and could in principle be replaced by a real camera. Streams are processed one at a time and the results stored for later search. Since the CPU-only target machine cannot analyse high-resolution video in real time, the demonstration data is indexed in advance from the dataset's video files through the same pipeline.
Forms of description. Users describe the person with one of three forms: · a pre-cropped reference image containing one person · a text description in English
3

· a set of predefined appearance attributes: gender, type and colour of the upper garment, type and colour of the lower garment, and carried items such as a backpack or a handbag.
The system does not support queries in Vietnamese and does not translate descriptions automatically.
Search results. Each result is one appearance of a person on one camera, ranked by relevance. Users choose the number of results and may restrict cameras and time range. The score only ranks results within a search the system draws no conclusion about identity, keeps no search history, and only stores results the user saves into a case file.
Users. The application serves several groups of users with different permissions, defined in Chapter 4. Managing the list of surveillance areas is out of scope the list is declared at deployment.
Deployment environment. A web application on a personal computer without a discrete graphics card, for demonstration, not commercial use.
Research on the search block. The research of Part II is a separate study of the search step for text descriptions and is not integrated into the application. It works on a public person re-identification dataset whose images are already cropped and grouped by identity, uses its own choice of models, and evaluates a re-ranking layer offline on a sample of identities. Its results show what such a layer could contribute to the search step they are not a measurement of the deployed application.
Out of scope. The project does not cover: · face recognition or determining the identity of the person in an image · searching for vehicles or objects other than people · training or fine-tuning artificial intelligence models · linking the appearances of the same person across different cameras in the application 4

· processing many camera streams concurrently and raising real-time alerts.
1.4 Limitations
Besides the defined scope, the results of the project have the following limitations their extent is quantified in Chapters 8 and 11 and summarised in Chapter 12.
· Search quality depends on existing models. The models were trained on data from contexts different from the project's camera data and are not fine-tuned, and the text model's re-ranking stage, which carries most of its accuracy, is optional because it is slow on the CPU. Search by text and by attributes is affected most, so search by image is the most reliable form.
· Narrow test data. The system was only tested on seven static cameras observing one outdoor place in daylight harder conditions such as low light or low resolution have not been verified.
· Not all cameras are analysed continuously. Running on a machine without a discrete graphics card, the system analyses video more slowly than it is recorded and processes the cameras in turn, so the searchable data of each camera has gaps.
· Appearances may be missed or split. The system analyses only part of the frames and represents each appearance by one frame, so a person who appears very briefly may be missed, and an occluded person may be split into several results or ranked low.
· Limited descriptions. Text descriptions are only supported in English the attribute set only covers gender, clothing and carried items, with no negative options.
· Relative scores and small deployment. The relevance score only ranks results within one search the system is deployed on a single computer at demonstration scale.
· The reasoning layer is evaluated offline and on a small sample. The research of Part II was measured on 100 identities of a public dataset with a hosted language

Chapter 3
Theoretical Background
This chapter presents the background of the application: person search and cross-modal retrieval, techniques for detecting and tracking people, frame sampling, joint image-text representation learning, vector search and the protocol used to stream camera video.
3.1 Person Search and Cross-Modal Retrieval
3.1.1 Problem Statement
Given a set of person images extracted from the video of many cameras, called the gallery G = {g1, g2, . . . , gn}, and a query q describing the person being sought, the system must rank the elements of G by how well they match q and return the k best matches. The common approach is to learn a representation function that maps the query and every element into a vector space, then measure relevance with a similarity function s(q, gi) search then becomes finding the nearest vectors.
In surveillance video, people are not tightly cropped as in benchmarks but appear in full frames among others, so the problem also includes detection. Xiao et al. learn detection and identification jointly [13], while another approach separates the detector from the identification model [14] the project follows the latter so that each component can be replaced independently.
3.1.2 Three Forms of Query
Search by image. When the query is an image containing the person, the problem corresponds to person re-identification (ReID): finding the images of the same person
14

in data collected from several cameras or at several times [15]. The main challenges are changes in viewpoint, lighting and pose, occlusion and low resolution: the same person can look very different between two cameras, while two people dressed alike can look very similar.
Search by text. When the user only has a verbal description, for example "a man wearing a black jacket and blue jeans, carrying a backpack", the problem is text-based person search (TBPS), proposed by Li et al. together with the CUHK-PEDES dataset of person images with English descriptions [16]. It is a cross-modal problem: the model must bring text and images into one representation space, while descriptions are often vague and the differences between people often lie in small details.
Search by attributes. The user picks attributes such as gender, garment type and colour, and carried items. They can be handled by a pedestrian attribute recognition model [17] filtering by label, which needs labelled data for every attribute, or turned into a sentence from a fixed template and searched as text. The project takes the second way to share the text model, so attributes affect the ranking but are not hard filters. Negative options such as "no backpack" are not supported, because CLIP-style vision-language models have considerable difficulty with negation, in many cases performing at chance level [18].
Unlike face recognition, appearance search relies not on biometrics, which need a visible face, but on clothing, colours and carried items, easy to see from high, distant cameras but changeable and shared by many people. Its results are suggestions to assess, not conclusions about identity.

3.2 Person Detection
3.2.1 Object Detection
Object detection locates the objects in an image and determines their class. For each object, the model returns a rectangular bounding box, usually given by the coordinates
16

of two corners (x1, y1, x2, y2), the class of the object and a confidence score. Two boxes are compared with the Intersection over Union (IoU):
IoU(A, B) = |A  B|, (3.1) |A  B|
which ranges from 0 when the boxes do not overlap to 1 when they coincide. IoU is used to remove duplicate predictions and to link detections across frames in tracking (Section 3.3).
3.2.2 Two-Stage and One-Stage Detectors
A two-stage model such as Faster R-CNN [20] first uses a region proposal network to generate regions likely to contain objects, then classifies each region and refines its box this is accurate but costly because many proposals must be processed. A one-stage model such as YOLO (You Only Look Once) [21] treats detection as a single regression problem, predicting the boxes and classes of all objects in one pass over the image, which is considerably faster and suits processing many video frames.
3.2.3 The YOLO Family
Modern YOLO models have three parts: a feature extractor (backbone) at several levels of detail, a feature aggregator (neck) at several scales so that both large objects close to the camera and small distant ones can be detected, and a prediction head for boxes, classes and confidence. YOLO11 was released by Ultralytics in 2024 in five sizes (n, s, m, l, x) that trade speed for accuracy [22]. The models are pre-trained on COCO [23], which has 80 common object classes including person, so they can detect people directly without further training.
3.2.4 Post-Processing: Thresholding and Duplicate Removal
The raw output has many low-confidence and overlapping boxes. Boxes below a confidence threshold are discarded, and Non-Maximum Suppression (NMS) keeps the most confident box and removes same-class boxes overlapping it beyond an IoU threshold. A lower confidence threshold misses fewer people but adds false detections a lower
17

IoU threshold removes overlaps more aggressively but may merge people standing close together.
3.2.5 Role of Detection in the System
The detector is applied to the sampled frames (Section 3.4) and keeps only the person class, with a confidence threshold of 0.1, an NMS IoU threshold of 0.7 and at most 300 detections per frame. The low threshold is deliberate: ByteTrack needs low-confidence detections, often partially occluded people, to keep tracks alive (Section 3.3) they never start tracks, and a track needs two observations to be confirmed, so most transient false detections are removed by tracking. The reasons for choosing YOLO11n are given in Section 6.1.4.
3.3 Multi-Object Tracking
3.3.1 Problem and Basic Components
A detector treats frames independently and cannot tell whether a person is the one seen before. Multi-Object Tracking (MOT) gives each object an identifier kept across frames the sequence of its boxes is a track, which in the project becomes an appearance, the unit of search results (Section 3.1.3).
The common approach is tracking-by-detection, founded on the SORT algorithm [24], which has three components. First, each track has a Kalman filter [25] that predicts the position and size of its box in the current frame under a near-constantvelocity assumption, then corrects the prediction with the actual detection. Second, the match between a track and a detection is measured by the IoU (Equation 3.1) between the predicted box and the detected box. Third, assigning each detection to at most one track at minimum total cost is solved with the Hungarian algorithm [26] an unmatched detection may start a new track, and an unmatched track is considered lost.
18

3.3.2 ByteTrack
Earlier methods discarded low-confidence detections, so partially occluded people often broke their tracks. ByteTrack [27] associates twice: high-confidence detections are matched with all tracks first, then the remaining tracks with low-confidence detections, so occluded people keep their tracks unmatched low-confidence detections are dropped as mostly background. Only high-confidence detections start tracks, and a lost track is kept briefly so it can resume.
3.3.3 BoT-SORT
BoT-SORT [28] extends ByteTrack by adjusting the Kalman filter state, compensating camera motion and adding appearance re-identification (ReID) features to the association step. In the project, BoT-SORT is an alternative tracker with the same thresholds as ByteTrack camera motion compensation and ReID are disabled because the cameras are static and to keep the cost low on a CPU-only machine.
3.3.4 Track Life Cycle in the System
The tracker receives the detections of the sampled frames, separately for each camera, with the following rules:
· Confidence thresholds: detections of 0.25 or more are high and may start a new track detections from 0.1 to below 0.25 are only used in the second association step.
· Confirmation: a track is confirmed only after at least two observations an unconfirmed track produces no result.
· Termination: a track ends after more than three lost processed frames or two seconds without observation, or when the stream ends. Both video files and RTSP streams use the timestamps recorded in the stream itself (Section 3.7.4), so the rule measures the time that passed in front of the camera and does not depend on how fast the machine processes.
19

· Identifier scope: one camera and one processing session only the system does not link the tracks of the same person across cameras.

3.4 Frame Sampling

The project's videos have about 60 frames per second, so consecutive frames are about 17 milliseconds apart and almost identical, and running the models on every frame is costly for little new information. Frames are sampled uniformly by index: frame i is selected with sampling interval N if and only if

i mod N = 0,

(3.2)

and it keeps its original index and timestamp, so that the time at which a person appears follows the camera's own timeline. With a source of f frames per second, two processed frames are N /f seconds apart: about 0.17 seconds with N = 10 and 0.33 seconds with N = 20.
The interval is a trade-off. Sampling precedes the detector, so model runs drop about N times, but every frame must still be decoded, since most H.264 frames depend on earlier ones (Section 3.7.1). A larger N misses brief appearances more easily, since a track needs two observations, and lets people move further between observations, making IoU association harder. The system provides two presets: baseline with N = 10, which favours track quality, and throughput with N = 20, which favours speed and was chosen as the default based on measurements on the target machine (Section 8.3). Each job records the value of N it used so that results can be compared and reproduced.

3.5.2 The RaSa Model
General models such as CLIP and ALBEF struggle with small differences between similar people, such as the same jacket over trousers of another colour. RaSa (Relation and Sensitivity Aware representation learning) [19] is built on ALBEF and designed specifically for text-based person search, with a 12-layer transformer image encoder, a 6-layer text encoder and a 6-layer multimodal encoder. Its three key points are:
· Intra- and inter-modal contrastive learning. Besides pairing images with sentences, images of the same person are pulled together, which is what lets the project use the same space for image queries.
· Relation-aware learning. A description is written for one image and may not hold for the person's other images, so RaSa treats these two kinds of positive pairs differently.
· Sensitivity-aware learning. The model learns to notice replaced key words, such as "red shirt" becoming "blue shirt".

The system uses RaSa weights pre-trained on CUHK-PEDES without retraining. The image encoder handles person crops at indexing and query images, resized to 384×384 pixels the text encoder handles descriptions and attribute sentences. 3.6 Vector Search
3.6.1 Nearest Neighbour Search and the HNSW Index
With one vector per appearance and a query vector q, search becomes k-nearestneighbour: find the k of n stored vectors with the largest inner product with q. Exhaustive search is exact but grows linearly with n Approximate Nearest Neighbor (ANN) search uses a prebuilt index to examine only part of the data, trading a few missed neighbours for speed.
HNSW (Hierarchical Navigable Small World) [31] is a graph-based ANN method: each vector links to some nearby vectors, and search keeps moving to a neighbour closer to the query. Sparse upper layers reach the right region quickly and the bottom layer, holding every vector, searches it precisely, so cost grows logarithmically with the data [31]. The index has three main parameters [32]: the maximum number of edges per node M and the number of candidates during construction efConstruction, which give a better graph when larger but cost more memory and construction time and the number of candidates during search ef, which is more accurate but slower when larger and should not be smaller than the number of results requested.
3.6.2 Vector Search with Filters
Surveillance queries carry conditions such as the user's area or a time range. Postfiltering takes the k nearest vectors overall and then drops those failing the condition, so it may return few or no results when the area is a small part of the data. Pre-filtering searches only among the vectors meeting the condition, so results fall short of k only when the scope really holds little data. Milvus [33], an open-source vector database, stores scalar fields next to the vectors and performs search with pre-filtering [34].
3.6.3 Vector Search in the System
The system uses Milvus with an HNSW index, the inner-product metric, M = 16, efConstruction = 128 and ef = 64. A search sends Milvus the query vector together with a filter made of the user's area, the permitted cameras, the time range if any and the ready
23

status, and receives at most k results with k  {4, 8, 12, 16}. The similarity, computed at query time, is shown as the relevance score. Each result is checked against PostgreSQL for its details and scope invalid results caused by temporarily unsynchronised stores are dropped, and if fewer than k remain, the search is repeated with twice the number, up to three rounds ef is raised to the number requested when the re-ranking stage of Section 5.2.3 asks for a pool larger than 64, up to 128. Exhaustive search would still suffice for the 1,523-track demonstration data (Section 7.2) HNSW keeps response times as data accumulates.
3.7 RTSP and Camera Stream Simulation
3.7.1 H.264 Compressed Video
IP cameras compress video, since an uncompressed 1920×1080 frame takes about 6 MB, or about 370 MB per second at 60 frames per second. H.264 [35] is the common standard and the project's format. An I-frame only uses prediction within the frame itself, so it can be decoded independently P-frames and B-frames only store motion and differences relative to reference frames, so they can only be decoded once their references are available. Decoding must therefore be done on every frame even though the system only analyses some of them (Section 3.4), and a decoder that joins a stream midway must wait for the next I-frame.
3.7.2 RTSP and RTP
RTSP (Real Time Streaming Protocol) [36] is a control protocol: the receiver identifies a stream by an address of the form rtsp://<host>:<port>/<path> and exchanges the DESCRIBE, SETUP, PLAY and TEARDOWN commands to obtain the description, set up, start and end the session. The data is carried by RTP (Real-time Transport Protocol) [37]: compressed video is split into packets with sequence numbers and timestamps for H.264 the timestamps use a 90 kHz clock [38]. RTP packets can be sent over UDP, with low latency but possible packet loss, or interleaved on the TCP connection of the RTSP session, without loss but possibly late under congestion. RTSP 2.0 [39] removed the commands
24

used to push a stream to a server, so the project's simulation tools use version 1.0.
3.7.3 Simulating Cameras with a Streaming Server
To test with the real protocol of IP cameras, each video is replayed as an RTSP stream acting as one camera. The MediaMTX streaming server [40] accepts streams pushed in and serves streams out over RTSP, each at its own path such as /cam1. The FFmpeg tool [41] reads the file and pushes it to MediaMTX with three options: -re to send at the original frame rate, -stream_loop -1 to loop forever like a camera that never stops, and -c copy to copy the compressed data without re-encoding, so the stream carries exactly the H.264 data of the original file and costs almost no resources. Like a real camera, the stream uses the same protocol and format and does not wait for a slow receiver unlike one, its content repeats and it suffers almost no packet loss or disconnection.
3.7.4 Receiving RTSP Streams in the System
The background worker reads streams with the PyAV library, which uses FFmpeg's decoding libraries, with RTP interleaved over TCP to avoid packet loss corrupting images. Connecting and waiting for data are both limited to 8 seconds when a stream is interrupted, the system tries to reconnect up to three times with a waiting time growing from 0.25 to 2 seconds, then records the processing run as failed. Each frame is timestamped from the stream's own presentation timestamp, anchored to the machine clock at the first frame of each session, so that the time between two processed frames is the stream time between them even when the machine falls behind a session that starts again after a reconnection or a restart of the source is anchored again, and only a frame without a usable timestamp falls back to the reception time (Section 3.3.4). Processing is much slower than the stream, so cameras share processing time as described in Section 5.2.1.

System Analysis
This chapter analyses the requirements of the system: actors, functional and nonfunctional requirements, the use case model and the permission matrix.
4.1 Actors
The system has three actors, one per kind of user account: the Administrator (Admin), the Operator and the Viewer. All three share one login function after login, the system only offers the functions and data of the account's role.
Two business concepts are used throughout the following chapters: · Surveillance area: a geographic scope such as a building or a public space. Each
camera belongs to exactly one area, set when it is added and never changed. Areas are declared at deployment the current version has no interface to manage them. · Case: a record in which an Operator keeps the search results related to an incident, with a title, notes and a status of Open or Closed. A case belongs to its Operator, not to an area: the area only limits the search scope. Since an Operator's area can change, a case may contain results from several areas.
4.1.1 Administrator
The Administrator keeps the cameras and the AI processing running for the other actors, and is responsible for:
· Accounts of Operators and Viewers, including the area of each Operator.
26

· Cameras and their RTSP connections.
· AI processing: which cameras are analysed, and the person detector (Detector) and tracking algorithm (Tracker) used by the whole system.
· Monitoring: the status of cameras and AI processing, checks of the AI components, and the audit log.
These technical rights do not include business rights: the Administrator cannot search for people or see cases. The Administrator account is created at deployment the interface can only create Operator and Viewer accounts.
4.1.2 Operator
The Operator uses the main function of the system: searching for people in the analysed camera data, assessing each result in the context of its frame, and saving the matching results into cases until each case is closed.
Two scopes limit the Operator. The search scope is the surveillance area of the account: only the operational cameras of that area are searched, and requests for other cameras or areas are rejected. The case scope is ownership: each case has exactly one Operator, its creator, who cannot transfer it. The two scopes are independent: after moving to another area, an Operator still manages his or her old cases, while new searches run in the new area.
4.1.3 Viewer
The Viewer is at management level, such as a head of department, and follows the results of the work without searching or configuring the system. The Viewer sees an overview of the cases of the whole system and every case with its saved results, read-only. Since cases are not tied to areas, the Viewer is not limited by area.
4.1.4 Principles of Role Separation
The division follows two principles: separating technical rights from business rights, so that those who configure the system do not see search data and those who use the
27

data cannot change the configuration and least privilege, so that each actor only has the rights its work needs. The permission matrix of Section 4.6 details these rights.
Cameras and the background AI processing are not actors: a camera is a data source configured by the Administrator, and the analysis runs automatically once AI processing is enabled.

System Design
This chapter presents the design of the system: the overall architecture, the main processing flows, the database, the application programming interface, the security mechanisms and the user interface.
5.1 System Architecture
Figure 5.1 shows the architecture, organised around the two stages of Section 3.1.3: the indexing flow (left) turns camera data into searchable appearances, the search flow (right) serves the user, and both meet at the storage layer. Black lines show indexing, blue lines search and data access, dashed lines the creation and claiming of jobs, and the thick line the continuous RTSP stream.
5.1.1 Components
· Camera data source. FFmpeg streams the test videos to a MediaMTX server each RTSP stream is a logical camera (Section 3.7.3), no different from a real IP camera for the system.
· Web application. A React interface shared by the three roles it only talks to the application server, never to a data store.
· Application server. A Flask process serves the API and keeps the RaSa encoder loaded for search queries.
45

Figure 5.1: Overall architecture of the system 46

· Background worker. A separate Python process runs all AI processing: it creates RTSP sessions in rotation among the cameras and runs the queued jobs one by one.
· Storage layer. PostgreSQL holds the business data and the job queue, Milvus the feature vectors with their filter fields, and MinIO the representative frame of each appearance.
5.1.2 Design Principles
The main principle is to separate AI processing from the application server. Analysis on the target machine is about seven times slower than real time, so the application server only creates jobs and the background worker runs them. Search stays available during indexing, and analysis errors cannot stop the server.
The job queue is a PostgreSQL table rather than a separate message queue, which means one less component to deploy and keeps job status next to the business data. The worker runs one job at a time, and bounded RTSP sessions rotate among the cameras so that each is analysed in turn without overloading the CPU.
Each store holds one kind of data, linked by a shared appearance identifier, and PostgreSQL is the source of truth (Section 5.3.4). Every data access, images included, goes through the application server, so the permission matrix of Section 4.6 is enforced at one point.
Finally, queries are encoded with the same RaSa weights as the indexed frames, so both lie in one vector space, and RTSP streams and video files share the pipeline after frame reading.
5.2 Main Processing Flows
5.2.1 Camera Data Processing Flow
All analysis runs as queued processing jobs, each tied to one camera and one source. For automatic RTSP sessions, when the queue is empty, the worker's scheduler picks the operational, AI-enabled RTSP camera that has waited longest and creates a session of 1,800 source frames (about 30 seconds at 60 frames per second) a camera whose
47

last session failed is skipped for 5 minutes. The cameras are thus analysed in turn, with unanalysed gaps between two sessions of one camera (Section 1.4). For uploaded video files, the application server checks and stages the file, then creates the job. Job life cycle. Figure 5.2 shows the states of a job. A Queued job claimed by the worker becomes Running with a 60-second lease, renewed during processing if the worker dies and the lease expires, the job can be claimed again. For a video file job, transient errors are retried after a delay, up to three times an RTSP session that fails ends at once, and the camera is processed again in a later session. A job ends as Succeeded as Failed after an unrecoverable error or exhausted retries or as Cancelled by the Administrator, or when its camera is retired or its AI processing disabled.
Figure 5.2: State diagram of a processing job Processing steps. Figure 5.3 shows the two phases of a job. In the per-frame loop, each frame is read with its index and timestamp (Section 3.7.4), and one frame in N goes through the Detector and Tracker. The result updates the track buffer, which holds the

active appearances and their representative frame candidates when an appearance ends, its representative frame is chosen and kept in memory. Appearances are therefore searchable only after their job ends for RTSP, a camera's data arrives session by session, every 1,800 frames. A job cancelled or expired during analysis writes nothing. 5.2.2 Representative Frame Selection
Each appearance stores one full frame, used both for the vector and for display, so it should show the person as clearly as possible. The selector works as follows:
· Keep at most three candidates per ongoing appearance, within 256 MB in total.
· Hard filters. A candidate needs a box of at least 24×48 pixels, a sharp enough person region, fewer than two frame edges touched, and no abrupt shape change from the previous observation (area within 4 times, aspect ratio within 2.5 times), which usually signals a wrong person or occlusion.
· The quality score weights the person's size (0.30), sharpness (0.25), body completeness (0.20), stability (0.15) and closeness to the middle of the appearance (0.10), minus penalties for touching the frame edges or overlapping other people.
· Choice at the end. The best candidate passing the filters is chosen if none passes, the best one is kept and the appearance is marked low quality rather than discarded.
The empirical criteria and weights are stored in a configuration file and give deterministic results.
5.2.3 Search Flow
Figure 5.4 shows the search flow. The web application sends the query with the camera filter, time range and k. The
server then: 1. validates the input: a JPEG or PNG image of at most 10 MB attributes from the allowed list forming a valid combination k in {4, 8, 12, 16}
2. encodes the query: images with the image encoder, descriptions with the text encoder attributes become an English sentence from a fixed template, such as "A woman wearing a red jacket and blue jeans, carrying a handbag."
3. determines the scope: the area comes from the Operator's account, and the cameras are the selected ones or every operational camera of the area others are rejected 50

Figure 5.4: Sequence diagram of the search flow 51

4. runs a pre-filtered vector search in Milvus, checked against PostgreSQL and repeated with twice the number when valid results are missing, up to three rounds (Section 3.6.3)
5. re-ranks text and attribute queries when the stage is enabled: the vector search returns a larger pool of N candidates (N between k and 128), the representative crop of each candidate is turned into image token features by the query encoder, kept in a disk cache per appearance, and scored against the sentence with RaSa's image-text matching head the pool is returned in that order, cut to k, with the matching score as the relevance score (Section 3.5.3). Image queries are not reranked.
The list only carries descriptive information and scores each image is a separate request, checked again and rendered from the representative frame (Section 6.3.2), so the list returns fast and no image skips the permission check.

5.3.4 Consistency Across the Stores
An appearance is stored in three parts across three stores that share no transaction, so writing may stop midway or a store may be unreachable. The system guarantees that incomplete data never appears in results and can later be completed or detected. Appearance states. Each appearance has a synchronisation state with the transitions of Figure 5.7 only Ready appearances are searched, and other transitions are rejected.
Figure 5.7: State diagram of an appearance
Write order. An appearance is written in a fixed order: 58

1. In one PostgreSQL transaction, create the record in the Pending state and an event in storage_outbox_events holding everything that must be written to the other two stores, the vector included. This is the transactional outbox pattern: the intent to write to another system is stored in the same transaction as the main data.
2. Write the frame to MinIO under its deterministic key.
3. Write the vector to Milvus, then read it back to confirm the record exists with the right area and camera.
4. In a new transaction, move the record to Ready, store the hash and size of the frame and the time the vector was written, and mark the outbox event as done.
Writing PostgreSQL first means every frame and vector matches a known record, so anything else is orphaned setting Ready last means an appearance is found only when complete. Steps 2 and 3 can be repeated safely thanks to the deterministic key and the upsert.
Error handling and maintenance tools. A transient failure in step 2 or 3 leaves the record Pending and schedules a retry, from 2 seconds doubling up to 300 seconds. After five attempts, or on an unrecoverable error such as a hash conflict, the record becomes Failed and is logged. Since the outbox event holds all the data, retries never rerun the analysis. Operators also have a command-line tool to complete pending appearances to reconcile the three stores, finding records pending for too long, ready records missing their frame or vector, and orphaned data (by default it only reports on request it quarantines broken records and deletes orphans) to move a failed appearance back to pending and to rebuild the Milvus data from the outbox events. These commands are currently run by hand.
Protection at search time. Even when the stores are out of sync, users see no wrong data: every Milvus result is checked against PostgreSQL, and missing or out-of-scope results are dropped (Section 3.6.3).

5.4 Application Programming Interface Design
The web application uses a REST-style API under /api/v1, with plural resource names such as /cases and Administrator APIs under /admin. Data is JSON, except images and videos sent as multipart/form-data. Business state changes such as retiring a camera are explicit actions, for example POST /admin/cameras/{id}/retire, each checked and logged on its own.
Errors share one format: a stable error code, a Vietnamese message, details such as per-field errors, and a request identifier matching the server log. Status codes keep their standard meaning: 401 without a valid session, 403 for a disallowed role, 404 for a missing or out-of-scope resource, 409 for a state conflict, 422 for invalid data and 429 over the call limit.
Updates to accounts, cameras and cases carry the version number held by the interface and get 409 if the data changed elsewhere. A video upload may carry an idempotency key, so a resend creates no second job, and is asynchronous: the server returns 202 with the job, whose progress the interface then follows.
A search response states whether the re-ranking stage of Section 5.2.3 was applied, since it changes what the relevance score means. No API takes the Operator's area or the case owner as a parameter (Section 5.5.3). Images of search results and of saved results have separate paths, matching the two grounds of Section 4.6.
Three health-check paths (/health/live, /health/ready, /health/storage) serve deployment and monitoring.
5.5 Security and Access Control Design
The security requirements of Section 4.3.1 and the permission matrix of Section 4.6 are implemented in defence in depth: each request is checked for its session, role and data scope, and database constraints are the last layer.
60

5.5.1 Authentication and Sessions
Passwords have at least 8 characters and are hashed with Argon2. An unknown username is still verified against a dummy hash and gets the same error as a wrong password, so neither timing nor message reveals which usernames exist.
A successful login yields a random 32-byte token in a cookie that is HttpOnly (unreadable by page scripts), SameSite=Lax (not sent with data-changing requests from other sites) and Secure over HTTPS. The database stores only its SHA-256 hash, so a leaked session table holds no valid token. A request gets 401 if its session is revoked, older than 12 hours or idle for 30 minutes, and the session is revoked at once if the account is locked, deactivated or an Operator without an area. While the user is active, the interface refreshes the session each refresh issues a new token with its own 12-hour limit and revokes the old one, so a leaked token is short-lived.
5.5.2 Cross-Site Request Forgery Protection
Because the browser sends the cookie automatically, another website could make it send requests to the system (CSRF). Besides SameSite, every data-changing request must carry an X-CSRF-Token header, an HMAC-SHA256 of the session token given to the interface at login, which other sites cannot read. Only the configured origins may call the API with cookies (CORS), and responses carry security headers that disable contenttype sniffing, framing by other sites and caching.
5.5.3 Access Control
Access control has three server-side layers. Each API declares its allowed roles and rejects others with 403 before any processing. The business layer then checks each object: cameras and appearances in the Operator's current area and operational, cases owned by the Operator, and images on one of the two grounds of Section 4.6 the area and owner always come from the session, never from the request, so editing a request cannot widen the rights. Finally, database constraints stop invalid data even if the business layer has a bug.
61

Objects outside the scope get 404 rather than 403, so trying identifiers reveals nothing about which objects exist.
5.5.4 Data Protection and Abuse Limitation
RTSP credentials are separated from the address, encrypted with Fernet under a key from an environment variable and decrypted only to connect they are never returned or logged. Since the connection check makes the server connect to a user-given address, only IP addresses in the declared camera ranges are accepted, and loopback, link-local and multicast addresses are always refused, so the check cannot probe the internal network (SSRF).
Costly or probe-prone functions are limited per minute: login 10 times per IPusername pair, and per account search 30, video upload 10, connection check 10 and AI check 6 times beyond that the server returns 429 with the waiting time. The counters live in process memory, which suits the single-process deployment. Query images must be JPEG or PNG within 10 MB and 24 megapixels, videos within 500 MB with a valid signature, and user file names are never used as storage paths.

Tracking. 6.2 Background AI Worker Implementation
Building on the job flow of Section 5.2.1, this section covers how the worker runs reliably on a CPU-only machine.
6.2.1 Model Management and Packaging
Only models declared in a model registry are loaded each entry records an identifier, version, weight file with its SHA-256 hash, preprocessing version and provenance with
68

the licence, and Trackers list their compatible Detectors. A model is usable only if its weight file exists, the hash matches, the licence is approved and a trial load succeeds others are shown as Unavailable. YOLO11n, ByteTrack, BoT-SORT and RaSa are usable, while the larger YOLO sizes and YOLOX have no weight files yet. The hash is rechecked whenever a pair is selected, so a replaced weight file cannot be used silently a new configuration is trial-loaded before saving, and each job keeps the configuration version current at its creation.
The RaSa checkpoint is loaded selectively. Its state is read from the file through a memory map, only the entries of the image encoder, the text layers of the text encoder and the two projections are kept (plus the cross-modal layers and the matching head when the re-ranking stage is enabled), and they are assigned to a module created without initial weights, so no random weights are allocated and then overwritten. A check against the full checkpoint loaded without selection, on 50 person crops and 10 sentences, gives identical vectors, so the selection does not change the vector space. One loaded encoder takes about 0.9 GiB, while loading as well as afterwards (Section 8.3).
Each kind of model sits behind an adapter with a common interface (open, process one input, close) that also checks the output: the Detector keeps only valid person boxes, and RaSa vectors must have 256 normalised, valid dimensions. Adding a model such as YOLOX thus needs only its weight file and a registry entry, plus an adapter for a new kind of model.
6.2.2 Resource Limits and Error Handling
The worker is bounded at several levels. Numerical libraries use 2 threads, leaving CPU cores for the server and the data stores. The Detector and image encoder run in a child process that is killed if an inference exceeds 120 seconds, since a call hung in a native library cannot be interrupted from inside. Each job runs in its own process with a 3,600-second deadline, and the operating system reclaims all its memory when it ends. Frames are released as soon as they are processed, except the bounded representative frame candidates.
Each error carries its step and an error code, stored with the job for the administration screens, and is classified in advance as transient or unrecoverable. Transient errors of
69

video jobs are retried from 5 seconds doubling up to 300 seconds, at most three times RTSP sessions are not retried, since that video has passed (Section 5.2.1). On a stop signal, the running job stays Running so it can be reclaimed after its lease expires, and a global PostgreSQL lock ensures a single executing process even if the worker is started twice.
AI check. The AI check screen trial-runs the models on real data without creating a job: for a camera, it reads up to 90 RTSP frames and runs the Detector, Tracker and image encoder on 6 of them for search, it encodes a sample image and description. A check takes at most 180 seconds, one at a time.

8.2 Search Quality Evaluation
8.2.1 Protocol
Method. The pipeline was run with the current configuration (YOLO11n at a confidence threshold of 0.1, ByteTrack, RaSa, every frame) on the labelled frames of the seven WILDTRACK cameras, 400 frames per camera, which produced a gallery of 1,526 tracks each track was given, for evaluation only, the majority person among its matched labels. The evaluation set has 26 queries, each in three forms: a cropped image, an English description and a set of attributes. The identities were chosen among people seen on all seven cameras with at least 30 labelled boxes, and their descriptions and attributes were written by hand from three crops on different cameras using only the attribute vocabulary of the application two identities walking next to a person dressed alike were left out. The observation used as the query image is removed from the gallery, and every other labelled observation of the same person is a correct result, 5 to 33 per query. Recall@k is the fraction of queries with at least one correct result in the top k, with k  {4, 8, 12, 16}, and MRR is the mean reciprocal rank of the first correct result text and attribute queries are tokenised with RaSa's own tokenizer (Section 3.5.3). With 26 queries one query is 3.8 points of recall, so Table 8.2 gives the 95% Wilson interval of Recall@8. An earlier run of the first six queries at a confidence threshold of 0.25, on a gallery of 1,552 tracks, gave the same picture: Recall@8 of 1.0 by image and 0 by text and by attributes.
Person detection and tracking. WILDTRACK labels people as positions on the ground plane and gives, for every fifth frame (400 per camera), the box of each labelled
82

person in each camera view. A detection counts as correct when it overlaps a labelled box of the same frame with an IoU of at least 0.5, boxes being matched one to one in decreasing order of IoU an unmatched detection is an extra box and an unmatched label a miss. At the confidence threshold of 0.1, the 2,800 labelled frames give 27,194 correct boxes, 35,602 extra boxes (2,278 of them second boxes on an already matched person) and 15,527 misses, a precision of 0.43 and a recall of 0.64 the earlier run at 0.25 gave 0.58 and 0.54. The precision is a lower bound rather than a measure of false detections: the labels only cover people inside the dataset's area of interest, and the cameras see many more, in the crowd on the steps behind the square in particular. In frame 400, for instance, about 19 of the 30 people visible on camera C1 and 3 of about 40 on camera C5 carry a label, and every correct detection of the others counts as an extra box. The recall is the meaningful figure: the lower threshold misses fewer labelled people, and the false and duplicate boxes it adds are mostly removed by tracking (Section 3.2.5). Of the 1,526 tracks, 491 match no labelled person (largely for the same reason), and 825 of the 1,639 labelled people are covered by at least one track the others are mostly people seen only briefly or far from the camera.

Two causes are established below: the application searches with RaSa's contrastive vectors alone, while the model's accuracy relies on its cross-modal re-ranker, and the domain gap between CUHK-PEDES, on which RaSa was trained, and the person images cropped automatically from the full frames of WILDTRACK. 8.2.3 Why Text Search Is Weak
Pipeline check on the training domain. To tell an implementation fault from the domain gap, the adapters that serve queries (image bytes through the image encoder, sentence through the text encoder, inner-product ranking) were run on 600 images of the CUHK-PEDES training split, the domain of the checkpoint, with their captions the published test split is not redistributed, and the copy used carries the captions of a person on each of that person's images, so retrieval is scored per identity. Three things follow. Image-to-image retrieval of the same person is perfect (Recall@1 of 1.000 on 109 queries), so the image side is right. Text-to-image retrieval by the vectors alone, as the application searches, reaches Recall@1 of 0.035 and Recall@10 of 0.177, against 0.002 and 0.017 for a random order: well above chance, far below the published 76.5%. Reranking the top 32 candidates with RaSa's cross-modal matching head, as the authors' evaluation code does over the top 128, raises Recall@1 to 0.650 on 40 of these queries over a 150-image gallery (contrastive vectors alone: 0.050), at about 0.2 seconds per candidate on the CPU. The published accuracy of RaSa therefore belongs to its re-ranker, which the application did not use the contrastive vectors that the vector search compares
84

are only its candidate generator. This, not an implementation fault, is the first reason text search is weak, before any domain gap. The check also found one difference from the authors' code: queries were tokenised with the standard BERT tokenizer, which closes a sentence with [SEP], while RaSa trains and evaluates without it using RaSa's own tokenizer raised Recall@10 on this sample from 0.137 to 0.177 and is now the default, with the image vectors and the index unchanged.
Where the vector search fails. Three further diagnostics on the same gallery and queries separate the crops from the encoder. First, crop size: the pipeline crops have a median height of 243 pixels (10th to 90th percentile 134 to 580) 1,100 of the 1,526 are shorter than the 384 pixels of the training crops and 122 shorter than 128, while the median aspect ratio of 0.38 is close to the training 0.33. Second, box tightness: cutting the same representative frames with the hand-drawn label box of the matched person instead of the detector box (possible for 947 tracks) moves text Recall@16 from 0.04 to 0.19 and the median rank of the first correct result from 73 to 67. Third, frame choice: a gallery made of the tallest label crop of each person on each camera, 1,439 crops of 266 people, gives text Recall@8 of 0.12 and Recall@16 of 0.19, with a median rank above 100. Tighter boxes and better frames help a little, but the vectors stay weak even on hand-picked crops, so what remains is the encoder's domain gap rather than detection or frame selection. The similarity scores say the same: the cosine of a text query with the 1,526 tracks has a mean of 0.19 and a standard deviation of 0.04, the correct tracks average 0.21 and the first result 0.30, so the right person stands less than half a standard deviation above the crowd, whereas on CUHK-PEDES a caption's own image stands a full standard deviation above the others (Section 3.5.3). Single-attribute queries make it visible: the top 16 of "A person wearing a red top" contains no red top, and the top-16 lists of six such colour queries overlap with a mean Jaccard index of 0.30, 47 distinct tracks filling their 96 places, mostly close crops of dark clothing and hair. The vectors rank by how much a crop resembles a training crop rather than by what the sentence says, which is what the matching head corrects below.

Timestamps of RTSP frames. Frames of an RTSP stream are timestamped from the stream's own presentation timestamps rather than from the time the system receives them (Section 3.7.4), because analysis runs about seven times slower than the stream. The difference was measured on the simulated stream of camera C1, reading 300 frames with an emulated processing time of 100 milliseconds per frame and the sampling interval N = 20: by reception time, consecutive processed frames were a median of 2,456 milliseconds apart, above the two-second termination rule for all 14 pairs by the stream's timestamps they were 334 milliseconds apart, the true spacing of 20 frames at 60 frames per second. With processing as fast as the decoder, both methods agree (409 against 334 milliseconds, the difference being decoding jitter). Chapter 9
Semantic Reasoning: Motivation
and Overview
This chapter opens Part II, the research on the search block. It states the problem and the contributions, reads the person search pipeline as a template of replaceable blocks, argues for improving the search block with a reasoning layer inspired by ZARA, and fills each block with a concrete model.
9.1 Motivation and Contributions
9.1.1 Problem
Given a free-text description such as "a teenage woman, with short hair, wearing a shortsleeve red top and shorts, with a bag" and a gallery of person crops from surveillance video, the task is to return the crops that show that person. This is text-based person search (Section 3.1), here over small, blurred, badly lit crops taken from arbitrary viewpoints.
9.1.2 Why a reasoning layer
A dual-encoder model such as CLIP encodes the sentence and every crop and sorts by cosine similarity. This is fast and the right first stage, but it has two limits.
· It gives one opaque number per crop. When the right person is ranked 37th, the score cannot say whether the top colour, the sleeves or the gender was misread, so 94

nothing can be corrected, and fine-tuning only changes the number.
· It ignores the track. Tracking groups crops of the same person seen under different blur, lighting and pose, but CLIP scores each crop alone and discards that redundancy.
An attribute-level representation addresses both: it is readable and can be aggregated across the frames of a track. The attributes, however, come from a small VLM and are noisy (Section 10.1.4), so they are aggregated by an LLM that reasons over evidence rather than by a majority vote.
9.1.3 Contributions
1. A statement of where the improvement should go: the pipeline is read as a template of replaceable blocks, and the search block is chosen because it must both generalise semantically and tolerate the errors of every block upstream (Section 9.2.2).
2. An attribute-centric index over tracked person crops: 18 attributes per crop read by Qwen2.5-VL-3B, with image-quality statistics per body region (sharpness, contrast, brightness, saturation) that let a later stage reason about why two readings disagree.
3. An adaptation of the ZARA evidence-and-reasoning pattern from motion-sensor activity recognition to image-text person retrieval (Section 9.2.3).
4. A four-stage multi-agent funnel (query analyst, feature selector, evidence reader, ranker) over two rounds with different cut semantics, with the prompt mechanisms that make it work: a citation rule, a reliability-not-direction ranking rule, a rarity table and a round-dependent coverage floor.
5. An evaluation protocol and tooling that rebuild every ranking from the saved model replies, and that separate retrieval from reasoning failures by reporting the pool ceiling next to every recall number.
6. A measured result on 100 identities, decomposed into what the layer rescues and what it costs, with an error analysis of both.

10.1.3 Three different counts

· Membership tells whether a query value red matches a frame that read [red, white], which it does.
The local (pool) prior is computed over deduplicated tracks, not pool crops: two crops of one five-frame track give a five-frame statistic, not a ten-frame one. Otherwise a person retrieved many times would dominate the pool statistic.

10.2 Multi-Agent Semantic Reasoning
10.2.1 The funnel
The reasoning block (Figure 10.1) keeps ZARA's coarse-to-fine iteration (Section 9.2.3), pruning before deciding, with four agents over two rounds:
1. The attribute-value selector (stage 1) chooses the pairs to spend evidence on, from the knowledge base and the pool statistics.
2. The evidence pruning agent (stage 2A) reads, for every candidate and pair, what this crop says and the evidence around that reading.
3. After the coarse cut (75  25), a second selector (stage 3) works on the survivors, whose statistics have changed with the pool. 104

4. The decision agent (stages 2B and 4B) ranks the candidates from the notes and returns the final ordering.
Figure 10.1: The semantic reasoning block. The knowledge base supplies per-attribute statistics to both selector calls the text query reaches the pruning and decision agents directly. Why stage 0 is not in the funnel. The query analyst (stage 0) is deliberately left out of the list and the figure: the funnel looks at candidates, and stage 0 never sees one. It is a pre-run over the query alone, once per query, settling how each query word relates to each index value. Its output is a lookup table read by every stage of both rounds, not a decision about any candidate, so drawing it as a fifth agent would wrongly suggest it prunes or ranks (Section 10.2.2).
The prompts themselves are not reproduced the rules that shape each stage are described below. Two properties drive their design. First, the coarse cut cannot be undone: a candidate placed 26th in round one is lost, while one ranked low in round two can still be returned, and the ranker is told this asymmetry in round-dependent terms (Section 10.2.5). Second, round two renumbers the survivors as candidates 1..M without their round-one labels, so the refine round is not anchored by the coarse ordering.

This is a statement about words: the analyst sees no candidate, image or statistic.

Why a separate pre-run. Every later stage must judge whether a crop's reading agrees with the query: the selector to weigh a pair, the evidence reader to place the query value, the ranker to size a conflict. Without stage 0, each call would derive the relation between, say, navy and black on its own, inside a prompt crowded with statistics, and the reader could treat a reading as a near match while the ranker treats it as a contradiction. Settling the relations once, from words alone, gives:
· Consistency: one relation per pair, read the same way by stages 1 to 4 in both rounds, instead of possibly different answers to the same question.
· Separation of concerns: deciding a relation without candidates, images or statistics keeps it free of bias from value frequency or pool content, so later stages reason about evidence, not vocabulary.
· Cost: the call depends only on the query and the vocabulary, so it is small, runs once and is replayed from disk on reruns (Section 10.2.8).
The most useful relation is near: it lets the reader and the ranker treat a likely describer confusion (navy read as black in a dim crop) differently from a real mismatch (navy read as red).

Four rules govern the note, each adopted after a measured failure:
1. The citation rule: never name a mechanism without the figure that shows it. This cut invented causes from 19 to 0 and mechanisms without numbers to 0 of 82, the clearest result in the pipeline it was also applied to the ranker.
2. The crop is a reference observation, not the truth: a frame agreeing with it proves nothing, since a tracker can group two people.
3. No deciding, ranking or averaging: the reader may not write correct, winner, most likely or therefore the person is X  it makes the evidence readable, and another stage orders it.

A single call with 75 candidates would exceed the free tier's token window, so stage 2A is split into three paced calls of 25 (Section 10.2.8), which is sound because no note depends on another.
10.2.5 Stage 2B: the ranker
The ranker sees only the query and one note per attribute per candidate: no per-attribute verdict, score or CLIP similarity. It ranks all N candidates and writes at least Nkeep = cap + 5 rows (30 of 75 in the coarse round, 15 of 25 in the refine round) as a markdown table with one reason each Nkeep is a minimum, and the model keeps writing while the evidence still separates candidates. Three mechanisms shape the ordering.
Reliability, not direction. Whether an attribute matches comes first, but the ordering rests on how much weight each reading can bear. Ranking on direction made 69 of 75 rows open with "Exact red top, shorts, female gender", shared by the whole pool and ordering nothing.
What each query value is worth. A rarity table at the top of the message gives, for each query value, its index share, the typical (median) share of its attribute, the most common share and the track stability, with a label, decisive ( 5× typical), moderate ( 1.5×) or almost nothing, and the ratio printed for checking. It was added after a measured failure: a candidate whose upper body was read as green in every frame, a rare colour, was ranked below candidates that only matched a common colour, because no stage carried any notion of rarity.
The coverage floor. The two rounds get different instructions about absence, because their cuts differ in kind.
· In the coarse round, PRESENT means read anywhere: in one frame, as a minority or overshadowed reading, in the track but not this crop, or as a [near] value. A present but weak reading ranks above an absent one. ABSENT is either read nowhere in the track (silence) or nothing closer than [far] read anywhere (contradiction). The floor applies only to the absence of a value the rarity table calls

decisive it is neither a count of matches nor a score.
· In the final round nothing lies below the cut to protect. A value read nowhere still pushes a candidate down a single overshadowed frame is weak positive evidence, weighed with the rest, not a floor.

10.2.8 Engineering
Three implementation details matter for reproducibility: · Replay by byte-identical input. Every stage saves its rendered input and reply a rerun replays each stage whose input is byte-identical and resumes at the first stage without a saved answer, so a run stopped by a quota limit continues without repeating calls. · Pacing. A rolling token-per-minute pacer holds back calls that would exceed the window, with 60 seconds between 2A batches, 180 seconds between identities, and exponential retry (60/120/240/480 s) on errors 503 and 429. · Robust parsing. Duplicate rows and short replies are reported as different failures a candidate skipped mid-list is appended in input order rather than dropped and an unparsable ranking falls back to the CLIP order with a warning, since an empty round would score like a wrong answer while hiding the failure.

Experiments and Results
This chapter presents the experimental setup on Market-1501, the results of the reasoning layer against the CLIP baseline with an analysis of what it rescues and what it loses, the ablations of its mechanisms, and the tooling that makes every number reproducible.
11.1 Experimental Setup
11.1.1 Dataset
The experiments use Market-1501 [51], with the attribute labels of the Market-1501_ Attribute project [52]: 1501 identities from six cameras on a university campus, with person boxes from an automatic pedestrian detector rather than drawn by hand.
Why Market-1501, and how it stands in for a tracker. The reasoning layer needs several crops of the same person grouped together, so that the frames of a track can agree or disagree about an attribute. Market-1501 labels every crop with its identity, and grouping by identity gives each person observations under different viewpoints, lighting, blur and occlusion, as a tracker would in the deployed pipeline.
The groups span up to six cameras, so they act as an ideal tracker that never switches or merges identities and follows a person across cameras. Their views differ more than the frames of a single-camera track, making disagreement between readings, which the funnel reasons about, more frequent rather than less. The third-party hand annotation of attributes [52] also makes an attribute-level error analysis possible.
113

Why YOLO11n and ByteTrack are not in the experiment. The experiment isolates the search block: the encoder, the retrieval of the candidate pool and the funnel behind it. Market-1501 already supplies the detected crops and the identity grouping that detection and tracking would produce, so running YOLO11n and ByteTrack would add nothing but their own errors. Every failure in Section 11.2.6 therefore belongs to retrieval or reasoning, at the cost of not measuring upstream errors at all (Section 12.3.2). Both remain the chosen blocks of the deployed pipeline (Table 9.2).
The 496-identity subset. We keep only identities uniquely identified by their annotated attributes, that is, whose attribute vector no other identity shares. This reduces 1501 identities to 496, the population behind every rate in this part.
The task must be answerable from the description alone. If two people are described identically, a query has two correct answers but the annotation records one, so returning the other would be marked wrong although it is right. Removing them removes noise the system cannot act on, but also makes the benchmark easier than the full 1501 identities, which matters whenever these numbers are compared with published Market-1501 results.
11.1.2 Models
The experiment runs the search-block entries of Table 9.2: CLIP ViT-H/14 (laion2B) as base encoder, Milvus as vector database, Qwen2.5-VL-3B-Instruct as attribute describer and Gemini Flash-Lite 3.5 as reasoning LLM at thinking level HIGH for every stage. Without this ceiling, retrieval and reasoning failures would look the same.

Accessories are the clearest case: carrying is unread 28% of the time, more often than its most common value backpack is read, so an accessory-based query favours candidates whose accessory happened to be described.

11.3 Ablations and Design Decisions
Almost every mechanism of Section 10.2 was added after a measured failure, and most can still be switched off. This section states what each changed and how strong the evidence is, separating what was measured from what is only switchable. Two limitations apply to all these numbers.
The sample behind a prompt measurement is a batch, not a sweep. The promptlevel numbers were collected while developing each stage, on batches of 25 to 75 candidates. They are large, categorical differences (19 to 0, 0 of 82), but not recall measurements over 100 identities.
The model fixes a style per call. Two back-to-back batches with the same prompt produced 0 of 73 and 73 of 73 notes with a boundary citation: the convention adopted at a call's first contested note holds for the rest of it. A/B comparisons of prompt wording must therefore span several calls, or they may only reflect this style lock.

11.4 Evaluation Tooling and Reproducibility
Two properties of the measurement setup changed results.
Records are rebuilt from replies, not trusted. The sweep writes one JSON record per configuration and one folder per query with every stage's rendered input and reply. Two notebooks writing the same record file caused a lost update: each held the whole file in memory, so the later save silently dropped the other's queries while the file still parsed and scored. The analysis notebook therefore ignores the record files and rebuilds every ranking from the per-query folders, mapping the ranker's labels back to crops by aligning the CLIP-similarity sequence of the saved prompt with the retrieval cache, position by position. A query whose alignment check fails is skipped and named, never guessed, since attaching labels to the wrong candidate list would produce a complete, plausible and wrong record.
125

Every rate is reported with its denominator and its ceiling. Queries without a ground-truth track are counted and excluded, not silently dropped, since a dropped query inflates every rate. cap@75 is stored per query, so any subset can recompute its own ceiling.
The supporting tools are: a per-identity viewer of the ground truth's CLIP rank and its rank after each stage with the ranker's reason a funnel-lost report of identities in CLIP's top 10 but not the funnel's (the source of Tables 11.3 and 11.4) a coverage table over all evaluated identities and a work-queue notebook classifying every full-pool query not yet evaluated as CLIP hit, miss but inside the pool (what reranking can still gain) or miss outside the pool (to be fixed in retrieval).

12.2 Achievements
12.2.1 Part I: The Application
Against the first five objectives set in Section 1.2, the application achieved the following: 1. The system turns camera data into searchable data. RTSP streams and video files go through the same pipeline of sampling, detection, tracking, representative frame selection and encoding, with a consistent write mechanism across the three data
127

stores. The demonstration data of 1,488 tracks from the seven WILDTRACK cameras was indexed without errors (Section 7.2).
2. All three forms of query, by image, English description and attributes, are implemented in one vector space. Search by image performs well (Recall@8 of 0.89 on 26 queries). Search by text and by attributes by the vectors alone is nearly ineffective on the test data with RaSa's matching head re-ranking the first 128 candidates, an optional stage added after the evaluation, text search reaches Recall@8 of 0.423 and attribute search 0.154, at about 17 seconds per query on the CPU (Section 8.2).
3. Users can view each result in its full frame and save results into case files with a status and an information snapshot. Viewers can follow these case files in readonly mode.
4. The three roles are controlled by the permission matrix of Section 4.6, with the search scope limited by area, and the access rule of every API is tested (Section 8.1). The Administrator has tools to monitor the status, check the AI and consult the audit log.
5. The project measured the search quality, processing speed and storage when integrating YOLO11n, ByteTrack and RaSa on a CPU-only machine (Chapter 8). The results clearly show the strength of search by image and the limitation of search by text, traced to the use of the model's vectors without its re-ranker and to the domain gap, with two measured ways forward.
The application runs the whole workflow from receiving camera data, searching and assessing to saving case files. The demonstration script ran automatically twice in a row with 15/15 steps passed, and the test suite of 740 unit tests together with the integration and end-to-end tests all passed.
12.2.2 Part II: The Reasoning Layer
For the sixth objective, the research of Part II reached the following result. Attribute-level evidence, rendered as text and reasoned over by a small LLM, recov-
ers 28 of the 67 identities that CLIP alone ranks outside its top 10, a gain of 23 points in
129

R@10, with no fine-tuning and on a pool produced by CLIP itself. The gain comes not from a better similarity measure but from readable evidence: what this crop and the rest of the track read, how strongly those frames link, and under what imaging conditions. The CLIP score, which the ranker does not use, separates the ground truth within its pool at an AUC of only 0.601: CLIP retrieves well but ranks its pool poorly.
The cost is small: five of the 33 identities already found by retrieval are pushed out, and four of them are recovered when only the two ranking calls use a larger model over the same evidence. Most of what remains is not a ranking problem: three of 100 identities were never retrieved, and the rest comes from attributes the describer could not read or did not write. Both causes are measurable, and with the ceiling reported next to every number, further work starts from a clearer position than the project did.
12.3 Limitations
12.3.1 Part I: The Application
The experiments confirm the limitations stated in Section 1.4. The largest is that search by text and by attributes is not yet effective on the test data: only one of the 26 text queries and no attribute query has a correct result in the top 16 (Section 8.2). Two causes were established (Section 8.2): the application searches with RaSa's contrastive vectors alone, whereas the model's published accuracy relies on its cross-modal re-ranker, which on the model's own training domain lifts Recall@1 from 0.05 to 0.65 and the domain gap between that training data and person images cropped automatically from cameras. The re-ranker is now available as an optional stage and brings text search to Recall@8 of 0.423 over 128 candidates, but at about 17 seconds per query on the CPU, which is too slow for interactive use unless the image tokens are precomputed at indexing time and the fusion passes run on a GPU.
On a CPU-only machine, processing is about seven times slower than real time. The system has to process the cameras in turn, part of the frames of a live stream are skipped, and the demonstration data had to be indexed from video files (Section 7.2). RTSP data is also only encoded and written at the end of each session, rather than as soon as each appearance ends, so there is a delay between a person appearing in front of a camera
130

and becoming searchable (Section 5.2.1). The first search needs a warm-up to load the encoder. The application processes take about 4.3 GiB while a job runs (Section 8.3), the server and the worker each hold a copy of the query encoder, and the Docker virtual machine adds 1.7 to 3.2 GiB depending on its uptime, so a 16 GB machine with other applications open remains tight.
Finally, BoT-SORT is integrated but has not been used for indexing or evaluated.
12.3.2 Part II: The Reasoning Layer
Model. The reasoning LLM is Flash-Lite 3.5, chosen for its larger free-tier allowance rather than its quality. Section 11.2.4 confirms the limitation, recovering four of five ranking failures by switching only the two ranking calls to a larger model a full sweep on that model, the most direct improvement, has not been run.
Data. Token limits restricted the evaluation to 100 of the 496 uniquely identifiable identities, so practical usability is not yet established, and the subset is easier than the full 1501 identities (Section 11.1.1). At n = 100 a percentage point is one identity, and the R@1 ordering of Table 11.2 rests on differences of 3 and 8 identities. Extending the sweep needs no new work: the work-queue notebook already picks the next identities, favouring those inside the pool but outside CLIP's top 10.
The blocks this part did not change. Detection and tracking were left as established defaults (Section 9.3.1), yet their failures reach the search block: a missed person has no crop, and a merged track holds two people. This part measures neither. A tracker-error analysis over the same 100 identities is the next measurement, and would move part of what Section 11.2.6 counts as a reasoning residue into an upstream category.
The refine round. Four stages beat two at R@10 and lose at R@1 and R@5, and three of the five losses in Table 11.4 come from the refine round. Whether stages 3 and 4 should return a full ranking, or only re-order the candidates the coarse round was unsure about, is still open.
131

Rarity versus mismatch cost. The rarity table tells the ranker what a query value is worth when it separates candidates, but not the converse: a binary attribute such as gender is "almost nothing" by rarity, both values being common, yet a gender mismatch is the strongest exclusion available. On one query, 40 of 40 reasons led with the lower colour and gender appeared in 2, while gender split the pool 44 to 31. This asymmetry remains to be handled.
Output truncation. At 25 candidates per 2A call, replies occasionally stop at the output limit mid-unit. The limit is detected afterwards from the API's finish reason, and the two direct fixes, an explicit output cap or batches of 15, have not been compared.
Single phrasing. Each identity is queried with one descriptive sentence, so robustness to paraphrase is not measured, although the pipeline already supports several phrasings per identity.
12.4 Future Work
12.4.1 Part I: The Application
The priority is to improve search by text and by attributes. RaSa's re-ranking with its multimodal encoder is now an optional stage of the search flow and is where the model's accuracy lies (Section 8.2) making it fast enough for everyday use means computing the image tokens of each appearance at indexing time, in the background worker, instead of at the first search, and running the fusion passes on a GPU, where 128 candidates take well under a second. The measurement of Section 8.2 also points to a simpler route: a second vector per appearance from a CLIP-like encoder, computed at indexing time and stored in its own Milvus collection, would give text and attribute search close to the re-ranked quality at the cost of one more vector search, while RaSa's vectors keep serving image queries the design already keeps one collection per encoder version, so the change is contained in the indexing pipeline and the query router. Fine-tuning either model on data from the same domain as surveillance cameras remains the step after that.
For memory, one encoder process shared by the application server and the back-
132

ground worker would remove one of the two copies of the query encoder, about 1 GiB. For speed, inference on the CPU could be optimised, for example with OpenVINO, starting with the image encoder, which takes most of the processing time (Section 8.3), or the system could be deployed on a machine with a GPU to analyse many camera streams at the same time instead of in turn. Once the system keeps up with real time, each camera could be processed continuously, and each appearance could be encoded and written as soon as it ends to shorten the delay before it becomes searchable. The write to the three stores already handles each appearance separately, so the change lies mainly in the analysis pipeline.
The evaluation should also compare ByteTrack with BoT-SORT. Further ahead, the system could link the appearances of the same person across cameras, represent each appearance with several frames, and support queries in Vietnamese.
12.4.2 Bringing the Two Parts Together
The research of Part II addresses exactly the weakest point of the application, search by text (Section 8.2). Its reasoning layer works on a candidate pool produced by vector retrieval, which is the output the application already obtains from Milvus, so it could be placed behind the application's search step as an optional re-ranking stage. Doing so would require an attribute index built alongside the vectors during indexing, a decision on where the language model runs given the application's on-premises deployment, and a measurement of the added latency per query. The further directions of the reasoning layer itself are stated in Section 12.3.2.
